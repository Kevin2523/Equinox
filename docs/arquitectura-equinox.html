01Resumen Ejecutivo y Stack Tecnológico

Verificado en código

Equinox es un CRM multitenant orientado a freelancers y estudios (incluyendo modalidad especializada de fotografía, desarrollo de software y diseño gráfico) con portal de clientes y consola de superadministración global. Su arquitectura separa estrictamente la capa de presentación (SPA Angular servida por Nginx), la API REST (Express 5 + TypeScript), la base de datos relacional (PostgreSQL 16 + Prisma 6) y el almacenamiento privado de binarios fuera del webroot.

03Flujos Paso a Paso

Verificado en código

A. Recorrido de una Petición de Usuario (HTTPS → PostgreSQL / Archivos)

1

Navegador / Móvil (SPA Angular 20)

El usuario accede a https://equinox.mena.date. Angular carga /assets/env.js (generado al iniciar el contenedor por frontend/docker-entrypoint.sh), que fija window.__EQUINOX_API_ORIGIN__ = window.location.origin cuando EQUINOX_API_ORIGIN=same-origin. El interceptor HTTP adjunta Authorization: Bearer <token> desde sessionStorage (clave equinox_sesion_token).

2

Cloudflare Tunnel + Terminación TLS (Pendiente activar dominio)

cloudflared en el servidor Ubuntu mantiene un túnel saliente hacia Cloudflare sin abrir puertos en el router. Enruta equinox.mena.date hacia http://127.0.0.1:8082 (producción), dejando intacto mena.date en :8080, e inyecta X-Forwarded-For y X-Forwarded-Proto.

3

Nginx Contenedor Frontend (frontend/nginx.conf)

Escucha en :80 dentro del contenedor (mapeado a 127.0.0.1:8082 en prod o :8081 en staging). Si la ruta es de SPA, aplica try_files $uri $uri/ /index.html. Si empieza con /api/ o /salud, hace proxy_pass http://backend:3000 por la red bridge interna equinox_net, con client_max_body_size 55M y proxy_request_buffering off para streaming de fotos.

4

Express 5 API (src/aplicacion.ts) y Middlewares

La petición pasa por helmet(), cors() (lista explícita ORIGENES_PERMITIDOS, rechaza *), express.json({ limit: "2mb" }), trust proxy validado por parsearConfiarProxy y morgan con redacción automática de tokens en URLs/Referers e IPs en rutas de invitación.

5

Validación de Sesión, Rol y Aislamiento Multitenant (src/middleware/autenticacion.ts)

exigirAutenticacion verifica firma JWT, valida la estructura con Zod y consulta la tabla sesiones en PostgreSQL (comparando token_hash SHA-256, revocada_en IS NULL y expira_en). Luego revalida en BD el rol real y verifica que organizacion.suspendidaEn === null.

6

Persistencia PostgreSQL 16 o Volúmenes Privados

Prisma consulta PostgreSQL filtrando siempre por organizacionId (y clienteId en /api/portal). Si es descarga de archivo o foto, Express lee el binario desde /data/archivos o /data/fotos mediante path.resolve estricto (nunca servido como estático por Nginx).

B. Flujo de Inicio de Sesión (Estándar, Multicontexto y Superadmin MFA)

1

POST /api/autenticacion/inicio-sesion con Rate Limiting Dual

Protegido por limitadorLoginIp (20 intentos / 15 min por IP) y limitadorLoginCuenta (5 intentos fallidos / 15 min por hash de correo). Compara contraseña con bcryptjs (incluye hash ficticio HASH_FICTICIO_BCRYPT para evitar enumeración por tiempo de respuesta).

2

Resolución de Contexto (ORGANIZACION, CLIENTE o ADMIN_GLOBAL)

Un mismo usuario puede tener membresía en organizaciones y acceso a portales de cliente. Si tiene múltiples contextos y no envió seleccion, la API devuelve la lista de contextos disponibles sin emitir JWT aún. Si tiene un único contexto (o envió seleccion), crea el registro en sesiones con tokenHash SHA-256 y devuelve el JWT (7d para org/cliente).

3

Flujo Obligatorio MFA TOTP para ADMIN_GLOBAL (/admin/acceso)

Si el usuario tiene rolPlataforma === "ADMIN_GLOBAL" y selecciona ADMIN_GLOBAL, el login no entrega JWT de sesión sino un token temporal DESAFIO_MFA_ADMIN (expira en 10 min) con propósito CONFIGURAR (primer ingreso: genera secreto Base32 + QR + códigos de recuperación) o VERIFICAR (código TOTP de 6 dígitos o código de recuperación). Solo tras verificar TOTP se emite el JWT administrativo (VENCIMIENTO_JWT_ADMIN=8h) con mfaVerificado: true.

C. Flujo de Despliegue: Desde Commit hasta Contenedor en Ejecución

1

Push / PR a develop o main en GitHub

main está protegida por ruleset (Proteccion de main (Equinox)) que exige PR y los 6 checks de ci.yml. cd-staging.yml dispara en develop; cd-production.yml dispara solo en refs/heads/main.

2

CI Gate (.github/workflows/ci.yml — 6 jobs)

Valida YAML/Compose, escanea secretos con Gitleaks, audita dependencias (npm audit --omit=dev --audit-level=critical), levanta postgres:16-alpine y ejecuta prisma migrate deploy + tsc + tests backend, compila Angular + 11 suites frontend, y verifica build Docker sin push.

3

Publicación en GHCR y Firma Cosign OIDC

Si vars.CD_IMAGES_ENABLED == 'true' (y en producción tras aprobación manual del reviewer Kevin2523 en environment: production), construye equinox-backend (target runner), equinox-migrator (target migrator) y equinox-frontend, los sube a ghcr.io y firma cada digest @sha256:... con Cosign OIDC keyless (Sigstore).

4

Agente Pull-Based en Ubuntu (equinox-cd@.timer → equinox-cd-pull.sh)

Cada ~2 minutos el timer ejecuta el script con flock. Consulta los digests en GHCR; si cambiaron, verifica la firma Cosign exigiendo issuer https://token.actions.githubusercontent.com y el ALLOWED_WORKFLOW_REF exacto. Descarga por digest inmutable, corre run --rm migrator, levanta up -d --remove-orphans, valida /salud/listo y /nginx-salud, y si algo falla ejecuta rollback automático a los digests previos.

04Tres Preguntas Clave de Operación

Explicación técnica directa

1. ¿Por qué hay 8 contenedores?

Porque coexisten 2 stacks completamente aislados en el mismo servidor Ubuntu, cada uno definido por compose.yml con 4 servicios (2 × 4 = 8):

  • Stack Staging (COMPOSE_PROJECT_NAME=equinox-staging, rama develop, puerto 127.0.0.1:8081): db + migrator + backend + frontend.
  • Stack Producción (COMPOSE_PROJECT_NAME=equinox-prod, rama main, puerto 127.0.0.1:8082): db + migrator + backend + frontend.

Cada stack tiene su propia red interna, sus propios volúmenes (pgdata, archivos, fotos) y su propia base de datos, sin interferir con el sitio raíz mena.date en :8080.

2. ¿Por qué migrator aparece como Exited (0)?

Es su comportamiento normal y esperado. En compose.yml, el servicio migrator tiene restart: "no" y ejecuta un único comando one-shot (node node_modules/prisma/build/index.js migrate deploy).

Una vez que db pasa su healthcheck (pg_isready), migrator aplica las migraciones pendientes, termina con código de salida 0 y se detiene. El servicio backend tiene depends_on: migrator: condition: service_completed_successfully, por lo que solo arranca cuando migrator ya terminó con éxito (exit 0). Además, esto permite que la imagen final de backend (target runner) no incluya la CLI de Prisma.

3. ¿Por qué la app sigue accesible cuando GitHub Actions terminó o parece no correr?

GitHub Actions no hospeda ni ejecuta la aplicación en producción. GitHub Actions únicamente valida el código, corre pruebas, construye las imágenes Docker y las publica en ghcr.io; al terminar, sus runners efímeros se destruyen.

Quien atiende a los usuarios 24/7 es el servidor Ubuntu LAN mediante los contenedores Docker con restart: unless-stopped (frontend + backend + db) y el túnel saliente de Cloudflare. Incluso si GitHub o GHCR estuvieran temporalmente inaccesibles, los contenedores ya descargados siguen sirviendo la aplicación normalmente.

05Frontend Angular 20 y Nginx

Implementado

El frontend es una Single Page Application (SPA) en Angular 20.3 compilada en build multi-etapa (frontend/Dockerfile) y servida por nginx:1.27-alpine. Soporta viewports desde 320px (viewport-fit=cover).

Rutas y Guards (frontend/src/app.routes.ts)

  • Públicas: /inicio-sesion, /registro, /recuperar-contrasena/:token, /invitacion/:token, /cerrar-sesion.
  • Freelancer (guardOrganizacion): /dashboard, /clientes, /proyectos, /tareas, /finanzas, /configuracion, /vista-previa-portal. Si tipoFreelance === 'FOTOGRAFIA', guardNoFotografia oculta dashboard/proyectos/tareas generales.
  • Cliente (guardCliente): /portal (ClientShellComponent + ClientHomeComponent).
  • Superadmin (guardAdminGlobal): /admin/acceso, /admin/resumen, /admin/organizaciones, /admin/usuarios, /admin/suscripciones, /admin/auditoria.

Configuración Runtime y Proxy Nginx

  • /assets/env.js: Generado en arranque por 40-equinox-env.sh con Cache-Control: no-store. Por defecto usa window.location.origin (EQUINOX_API_ORIGIN=same-origin).
  • Proxy inverso (frontend/nginx.conf): Reenvía /api/, /salud y /salud/listo a http://backend:3000 preservando Host, X-Real-IP, X-Forwarded-For y X-Forwarded-Proto.
  • Cabeceras de seguridad: server_tokens off, X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN, Referrer-Policy: no-referrer.
  • Subida de fotos: client_max_body_size 55M y proxy_request_buffering off para transmitir binarios sin buffering en disco de Nginx.

06Backend API, Autenticación, MFA y Multitenancy

Implementado

Seguridad de Plataforma (src/aplicacion.ts)

  • CORS estricto: En producción exige ORIGENES_PERMITIDOS explícito; prohíbe comodín * y orígenes vacíos.
  • CONFIAR_PROXY: Validado por parsearConfiarProxy(); acepta únicamente false, 0 o entero de 1 a 10 (1 con Nginx, 2 con Cloudflare + Nginx).
  • Logs sanitizados (Morgan): Redacta tokens en rutas /invitacion/*, /api/portal/*, /recuperar-contrasena/*, ?token= y encabezados Referer, además de redactar IPs en rutas públicas de invitación.
  • Rate Limiting (src/middleware/rate-limit.ts): Almacén en memoria acotado (límite 5000 claves) con soporte opcional para Redis/Valkey vía REDIS_URL.

Sesiones, Roles y Multitenancy

  • 3 Contextos de Sesión: ORGANIZACION (PROPIETARIO / COLABORADOR), CLIENTE (TITULAR / COLABORADOR) y ADMIN_GLOBAL (con MFA TOTP obligatorio).
  • Sesiones revocables en BD: Cada JWT contiene sesionId y se valida en cada request contra la tabla sesiones (tokenHash SHA-256, revocadaEn, expiraEn).
  • Aislamiento en BD: Todas las entidades de negocio incluyen organizacionId. Las tablas accesos_cliente e invitaciones_cliente usan FK compuestas (cliente_id, organizacion_id) hacia clientes(id, organizacion_id).
  • Suspensión de organización: Si organizacion.suspendidaEn !== null, exigirAutenticacion bloquea el acceso con HTTP 403 tanto a miembros como a clientes.

07Portal del Cliente y Almacenamiento Privado

Implementado

Archivos de Proyecto (src/almacenamiento/archivos.ts)

  • Volumen: equinox_archivos montado en /data/archivos (EQUINOX_ARCHIVOS_DIR). En producción falla con 503 si no está definido.
  • Validación estricta: Límite de 8 MB, validación de magic bytes para PDF, PNG, JPG, WEBP, GIF y UTF-8 válido para TXT.
  • Claves y descarga: Se guardan como <uuid>.<ext> con permisos 0600 y referencia local:<clave> en BD; se sirven únicamente tras validar sesión y pertenencia al proyecto.

Fotografía en Streaming (src/servicios/almacenamiento-fotos.ts)

  • Volumen: equinox_fotos montado en /data/fotos (ALMACENAMIENTO_FOTOS_DIR).
  • Streaming sin Base64: Límite configurable ALMACENAMIENTO_MAX_BYTES (por defecto 50 MB). Lee cabecera (primeros 32 bytes) para detectar MIME real (JPEG, PNG, GIF, WEBP, TIFF, AVIF) y escribe archivo temporal antes de renombrar a <uuid>.bin.
  • Sin URLs públicas: El frontend descarga las fotos mediante fetch autenticado con JWT como Blob y genera URL.createObjectURL().

En el portal (/api/portal), el cliente solo visualiza proyectos propios, hitos con visibleEnPortal: true, archivos con visibilidad: 'CLIENTE', facturas cuando la organización tiene portalMostrarFinanzas: true (expuesto en cabecera X-Portal-Finanzas) y sesiones fotográficas en estado PUBLICADA.

10Matriz Explícita: Implementado vs. Pendiente

IMPLEMENTADO (Verificado en el repositorio y GitHub)

  • Backend Express 5, Auth JWT, MFA TOTP, recuperación, multitenancy, portal y streaming de fotos.
  • Frontend Angular 20 responsive, env.js runtime y nginx.conf con proxy /api/ y 55M.
  • Esquema Prisma con 23 modelos y 11 migraciones SQL aplicadas y validadas en CI.
  • Dockerfile.backend (multi-stage builder, migrator, runner) y frontend/Dockerfile.
  • compose.yml + compose.prod.yml con aislamiento de puertos (127.0.0.1:8081/8082).
  • .github/workflows/ci.yml, cd-staging.yml, cd-production.yml con Cosign OIDC.
  • Scripts Pull-Based CD en deploy/cd/ (equinox-cd-pull.sh, equinox-cd@.service, equinox-cd@.timer).
  • Ruleset de rama main y environments staging / production documentados en docs/OPERACION_CICD.md.

PENDIENTE (Activar fuera del código o en servidor/host)

  • Integración Git de deploy/cd/*: Commit/push de los artefactos de Pull CD si aún están en rama de trabajo y limpieza de jobs SSH legacy.
  • Variable GitHub: Activar CD_IMAGES_ENABLED=true en Repository Variables cuando se desee publicar a GHCR.
  • Instalación Pull CD en Ubuntu: Instalar cosign, copiar script a /usr/local/sbin/, units a /etc/systemd/system/, crear /etc/equinox-cd/{staging,production}.env y habilitar timers.
  • Archivo .env de Producción: Crear /opt/equinox-prod/.env (POSTGRES_PASSWORD, SECRETO_JWT, URL_BASE, ORIGENES_PERMITIDOS, FRONTEND_PORT=8082).
  • Cloudflare Tunnel: Configurar equinox.mena.date → http://127.0.0.1:8082 en cloudflared (manteniendo mena.date en :8080).
  • Bootstrap inicial de BD: Primer arranque en producción y ejecución única de npm run admin:bootstrap -- --correo <email> --confirmar.
  • Backups automatizados y SMTP: Programar cron de pg_dump -Fc + snapshot de volúmenes; configurar SMTP_HOST (actualmente vacío, recuperación devuelve 503).

11Operación, Backups y Recuperación ante Fallos

Observabilidad y Verificación

  • Logs CD: sudo journalctl -u equinox-cd@production -n 100 --no-pager
  • Estado de contenedores: docker compose -p equinox-prod ps (migrator debe figurar Exited (0); db, backend, frontend en Up (healthy)).
  • Salud local: curl -fsS http://127.0.0.1:8082/nginx-salud y http://127.0.0.1:8082/salud/listo.
  • Estado Pull CD: /var/lib/equinox-cd/<env>.state guarda CURRENT_*_DIGEST, PREV_*_DIGEST y FAILED_*_DIGEST (evita bucles de rollback).

Backups y Recuperación

  • Respaldo BD (docs/MIGRACIONES.md): pg_dump -Fc -v -f equinox_backup.dump ejecutado dentro o contra el contenedor db antes de migraciones mayores.
  • Respaldo de volúmenes: Snapshot o tar de equinox_pgdata, equinox_archivos y equinox_fotos.
  • Rollback de aplicación vs BD: equinox-cd-pull.sh revierte automáticamente las imágenes de contenedores al digest anterior si falla el healthcheck, pero Prisma es forward-only (no hace migrate down).
  • Fallo de migración: Consultar npx prisma migrate status y seguir protocolo de docs/MIGRACIONES.md (rollback transaccional o prisma migrate resolve).

12Glosario Técnico y Referencias del Repositorio

TérminoDefinición en el contexto de Equinox
One-shot (migrator)Contenedor con restart: "no" que ejecuta una tarea finita (prisma migrate deploy) y finaliza con código 0.
Digest Pinning (@sha256:...)Fijación de una imagen Docker por su hash SHA-256 inmutable en lugar de un tag mutable como :latest.
Cosign OIDC KeylessFirma criptográfica de imágenes OCI mediante identidad efímera OIDC de GitHub Actions y registro público Sigstore/Rekor, sin claves privadas estáticas.
Pull-Based CDModelo donde el servidor destino consulta periódicamente el registro (ghcr.io) y descarga cambios, eliminando acceso SSH entrante desde CI.
Multitenancy por FK CompuestaAislamiento entre organizaciones reforzado en PostgreSQL mediante claves foráneas compuestas (cliente_id, organizacion_id).
Same-Origin (env.js)Patrón donde el frontend Angular consulta /api/ sobre el mismo dominio que lo sirvió, delegando el enrutamiento al proxy Nginx.
